## День 1 — Аудит текущего кода

### 1. Что уже есть и выглядит пригодным для повторного использования
- `scripts/abo150_vlm_validation.py` — основной reusable-кандидат для пайплайна инференса и оценки.
- `ABO150_Validation_Colab.ipynb` — рабочая обёртка под Colab для `dataset/abo_150_expanded`.
- `scripts/update_abo150_panel_paths.py` — завершённый утилитарный скрипт для исправления `panel_path`.
- `scripts/build_abo_physics_subset.py` — отдельный генератор subset-датасета под старый протокол.
- `CourseWork.ipynb` — полезный источник логики по unified model registry, отчётам и Comet.

### 2. Что уже реализовано в `scripts/abo150_vlm_validation.py`
- Загрузка ontology из YAML.
- Нормализация категориальных, boolean и multi-categorical значений.
- Единый registry моделей.
- Единый inference pipeline для нескольких HF VLM.
- `joint` и `per_property` prompt mode.
- Batched inference для per-property режима.
- Сохранение per-sample CSV, property-level CSV и summary JSON.
- Логирование в Comet.

### 3. Что уже помогает для Day 1, но ещё не закрывает требования PDF
- Есть `coverage`-подобные метрики через `pred_yes_pct` и `coverage_on_gt_known_pct`, но нет полного набора метрик из PDF в явном виде.
- Есть zero-shot pipeline, но few-shot как отдельный воспроизводимый режим пока не оформлен.
- Есть `raw` и `masked`, но нет отдельного `mask-overlay`.
- Есть большая ontology и большой датасет, но это не совпадает 1-в-1 с компактным словарём свойств из PDF.

### 4. Что выглядит как главные разрывы между PDF и текущим кодом
- Нет компактного основного task-schema на 13 свойств из PDF.
- Нет отдельного few-shot evaluation protocol.
- Нет `macro-F1`.
- Нет `selective accuracy` в явном виде.
- Нет отдельного режима `mask-overlay`.
- Ноутбуки остаются главным entrypoint, хотя логика уже частично вынесена в `scripts/`.

### 5. Что нужно рефакторить в первую очередь
- Вынести task-schema и mapping свойств в отдельный слой конфигурации.
- Разделить "экспериментальный протокол из PDF" и "широкий exploratory pipeline на ABO150 expanded".
- Добавить вычисление требуемых метрик в одном месте и использовать их и в ноутбуках, и в CLI/скриптах.
- Добавить few-shot prompt builder и воспроизводимый выбор демонстрационных примеров.
- Добавить третий режим визуального входа `mask-overlay`.

### 6. Что можно не трогать на Дне 1
- Полноценное дообучение.
- Глубокую переработку датасета.
- Большой косметический рефактор ноутбуков.
- Оптимизацию скорости beyond basic stability.

### 7. Что блокирует День 2
- Отсутствие зафиксированного компактного evaluation protocol на свойства из PDF.
- Отсутствие ready-to-run few-shot режима.
- Неполный набор метрик.
- Неполный набор режимов визуального входа.

### 8. Оценка текущего состояния
- Инженерная база уже достаточно сильная, чтобы не начинать проект заново.
- Самая правильная стратегия — не переписывать всё, а быстро довести существующий `scripts/abo150_vlm_validation.py` до статуса "ядро протокола", а ноутбук оставить как orchestration layer.

## Решение Дня 1
- Основной reusable слой проекта — `scripts/abo150_vlm_validation.py`.
- `ABO150_Validation_Colab.ipynb` остаётся пользовательской точкой запуска в Colab.
- На День 2 нужно целенаправленно добить protocol features, а не делать общий рефактор ради рефактора.
